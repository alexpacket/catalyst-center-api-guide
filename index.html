Foundations

Overview and the four interfaces

Catalyst Center exposes a northbound REST (Representational State Transfer) API over HTTPS with JSON bodies, called the Intent API. Around it sit an eastbound event channel, a westbound ITSM (IT Service Management) integration, and a southbound multivendor SDK (Software Development Kit) that Cisco has deprecated. Every call goes to https://<cluster> plus a path prefix.

PrefixServesExample
/dna/intent/api/v1/ (v2)Automation and inventory: sites, devices, provisioning, SD-Access, wireless, templates, eventsGET /dna/intent/api/v1/network-device
/dna/data/api/v1/Assurance analytics: query, count, trend, top-N, energyPOST /dna/data/api/v1/assuranceEvents/query
/dna/system/api/v1/ (v2)Platform: authentication, users and roles, backup and restore, system upgradePOST /dna/system/api/v1/auth/token
/dna/campus/api/v1/New in the 3.3.x Platform User Guide (campus networks)POST /dna/campus/api/v1/networks

Naming shifted in 2.3.7: older operations use hyphenated singular paths (/network-device); newer ones use camelCase collections with /count and /query siblings (/networkDevices, /networkDevices/query). Prefer the newer form; the older ones are the usual deprecation candidates.

Foundations

Where a call stops

Most reads are answered from the controller's own stores and never touch a device. Writes and live CLI (command-line interface) queries become tasks, and only tasks reach devices. Cost, freshness and safety all follow from which path you hit.

Inventory and design DB

Sites, settings, devices, configuration archive. Paged with offset/limit (max 500).

Freshness: last device sync. Periodic resync minimum is 6 hours from 3.1.5, plus event-driven updates.

Assurance data

Health scores, issues, events, analytics. Intent health endpoints plus /dna/data query and trend operations.

Freshness: telemetry ingest from devices (SNMP, syslog, NetFlow, streaming telemetry).

Task engine

Provisioning, SWIM (Software Image Management), discovery, Command Runner. Returns 202 with a taskId.

Freshness: the result exists only once endTime is set.

Live simulation: a day of API traffic

The same three stores, running. Devices stream telemetry into Assurance without any API call. Your dashboard polls every five minutes, a CMDB (configuration management database) sync pages through inventory nightly, and webhooks leave the event engine without touching the API gateway. Trigger a Command Runner job or a 60-call bulk script to see the default limit of 50 calls per minute reject the overflow with HTTP 429.

Authentication and RBAC

Authenticate once with HTTP Basic (RFC 7617), then send the returned JWT (JSON Web Token) in X-Auth-Token on every call for up to one hour. Every call is then checked against the caller's RBAC (Role-Based Access Control) role.

ItemDetail
Token endpointPOST /dna/system/api/v1/auth/token with Basic credentials; response {"Token": "..."}
HeaderX-Auth-Token: <token> plus Content-Type: application/json
Lifetime1 hour per the Authentication API specification. The 3.3.x Platform User Guide's API prerequisites page states 60 seconds. Treat the lifetime as unreliable: cache the token, and re-authenticate on any 401.
Code previewsDeveloper Toolkit generates code in Shell, Node, Python, Ruby, JavaScript, jQuery, PHP, Go and Ansible. Generated Python needs the requests library.
Optional AES modeIf enabled in system configuration, the Authorization header carries a Base64-encoded 256-bit AES (Advanced Encryption Standard) key instead of Basic credentials.
RBACUse RBAC v2 roles (/dna/system/api/v2/roles) and access groups (/dna/system/api/v1/accessGroups) from 3.1.5; v1 role operations are Sunset.
Getting a token for testingPlatform > Developer Toolkit > Authentication > Authentication API > Try, or Postman / Bruno with Basic auth. Cisco's tech note sets the token once as a collection-level header.
Service accountsCisco's lab examples use a SUPER-ADMIN login; in production use one account per integration. Observer role for read-only collectors and MCP; a narrow custom role for writers.
TLS (Transport Layer Security)Labs disable verification for self-signed certificates; in production import the cluster CA (Certificate Authority) and keep verification on.
Python · minimal client used by every example in this guide
# catalyst_client.py: token cache, 401 re-auth, 429 backoff, task poller, pager
import json, time, requests
from requests.auth import HTTPBasicAuth

class CatalystCenter:
    def __init__(self, host, user, password, verify=True):
        self.base = f"https://{host}"
        self.s = requests.Session(); self.s.verify = verify
        self.auth = HTTPBasicAuth(user, password); self.exp = 0

    def _login(self):
        r = self.s.post(f"{self.base}/dna/system/api/v1/auth/token", auth=self.auth)
        r.raise_for_status()
        self.s.headers.update({"X-Auth-Token": r.json()["Token"],
                               "Content-Type": "application/json"})
        self.exp = time.time() + 55 * 60          # token lives 60 min

    def call(self, method, path, **kw):
        if time.time() > self.exp:
            self._login()
        delay, relogged = 2, False
        for _ in range(6):
            r = self.s.request(method, self.base + path, **kw)
            if r.status_code == 401 and not relogged:
                self._login(); relogged = True; continue
            if r.status_code in (429, 503):       # no rate-limit headers: back off
                time.sleep(delay); delay = min(delay * 2, 60); continue
            r.raise_for_status()
            return r.json() if r.content else {}
        raise RuntimeError(f"gave up: {method} {path}")

    def wait_task(self, task_id, timeout=900, every=5):
        t0 = time.time()
        while time.time() - t0 < timeout:
            t = self.call("GET", f"/dna/intent/api/v1/task/{task_id}")["response"]
            if t.get("endTime"):
                if t.get("isError"):
                    raise RuntimeError(t.get("failureReason"))
                return t
            time.sleep(every)
        raise TimeoutError(task_id)

    def pages(self, path, params=None, limit=500):
        offset = 1                                 # offset is 1-based
        while True:
            rows = self.call("GET", path, params={**(params or {}),
                             "offset": offset, "limit": limit})["response"]
            yield from rows
            if len(rows) < limit:
                return
            offset += limit

Foundations

Async tasks, pagination, rate limits

Every write is a task

A 202 Accepted means the request was queued, not that it worked. Poll the task until endTime is set and check isError. Orchestration (business) APIs such as SD-Access return executionId and executionStatusUrl instead; poll /dna/intent/api/v1/dnacaap/management/execution-status/{executionId}.

Pagination and filtering

RuleDetail
Page sizelimit 1 to 500 on the list operations checked (for example validation workflows, SD-Access virtual networks). Not a global rule: read each operation's limit.
Offsetoffset is 1-based. Loop until a page returns fewer than limit rows.
Size firstCall the matching /count operation to size a job.
Complex filtersPrefer POST …/query operations for filters, sorting and aggregation.
Known issue3.2.3 release notes: repeated calls with the same limit and offset can return different site IDs; a documented sort parameter was reported unsupported. Sort client-side and de-duplicate by ID.

Rate limits

SourceWhat it says
OpenAPI specs on DevNetPer operation: many show 100 requests per minute, some 50 per minute
Platform User Guide 3.2.x and 3.3.x"The intent APIs have a default API rate limit of 50 requests" (no time window stated); per-operation limits are on the Features tab in Platform > Developer Toolkit > APIs
Python SDKWaits and retries on 429 by default (CATALYST_CENTER_WAIT_ON_RATE_LIMIT)
HeadersNo rate-limit response headers are documented. Treat 429 as normal and back off.

Rate-limit budget calculator

Default 50 per the Platform User Guide; read the real limit on each operation's Features tab. Per-record detail calls are what usually blow the budget.

Automate

Templates and provisioning Writes config (async) Reaches the device

Configuration templates (CLI or Velocity/Jinja) are the main way to push custom configuration in both fabric and non-fabric networks. The safe sequence is author, version, preview, then deploy.

  1. Create a project and template in Template Programmer
  2. Commit a version (deployments use committed versions)
  3. Preview the rendered config for one device
  4. Deploy to devices or by site; get a task
  5. Poll the task, then run compliance
Endpoint familyFunction
GET /dna/intent/api/v2/template-programmer/projectFind projects and template IDs
POST /dna/intent/api/v1/template-programmer/template/deployDeploy a committed template; returns a deployment ID
GET /dna/intent/api/v1/template-programmer/template/deploy/status/{deploymentId}Poll deployment status until it reports success or failure
Network profiles and site assignmentBind templates to sites through profiles so new devices inherit them
Wired and wireless provisioning operationsAssign a device to a site and push the site's intent

Template deployment is tracked by a deployment ID and its own status endpoint, not by the generic task API. Template variables are usually filled from a CMDB or IPAM record. Keep templates idempotent and avoid lines that the controller's own intent also writes, or compliance will flag drift.

Yes for the platform, no for the overlay. Authentication, sites and settings, inventory, discovery, PnP, templates, SWIM, compliance, Assurance and events are the same operations in both. Events and webhooks Stops at the controller

When a subscribed event fires, Catalyst Center makes an HTTP POST or PUT to your listener with a JSON payload. Destinations can be REST webhook, email, syslog, SNMP trap or Webex (listed in the 3.3.x Platform User Guide), plus ITSM. Event definitions are fixed and cannot be edited.

Python · register a webhook, subscribe, reconcile
# Illustrative payloads: confirm field names in Platform > Developer Toolkit > APIs
hook = cc.call("POST", "/dna/intent/api/v1/event/webhook", json={
    "name": "noc-listener", "description": "NOC event intake",
    "url": "https://hooks.example.com/catc", "method": "POST",
    "trustCert": True})
cc.call("POST", "/dna/intent/api/v1/event/subscription/rest", json=[{
    "name": "network-device-unreachable",
    "subscriptionEndpoints": [{"instanceId": WEBHOOK_ID,
        "subscriptionDetails": {"connectorType": "REST"}}],
    "filter": {"eventIds": ["NETWORK-DEVICES-3-506"]}}])

# Hourly reconcile: pull what the webhook may have missed
events = cc.call("GET", "/dna/data/api/v1/assuranceEvents",
                 params={"deviceFamily": "Switches and Hubs",
                         "startTime": int((time.time() - 3600) * 1000)})

Cisco's stated practice: confirm HTTP/HTTPS reachability from the cluster to your listener before subscribing. An HTTP/S proxy can be set for outbound notifications. The event ID above is an example; pick IDs from Platform > Developer Toolkit > Event Notifications > Event Catalog.

Troubleshooting tools Reaches the device

Command Runner runs read-only CLI commands on devices; Path Trace (POST /pathTraces from 3.2.2, POST /flow-analysis earlier) analyses the path between two endpoints. Both are tasks that reach devices: run them for one device or flow, on demand, never on a schedule.

Python · Command Runner
cc = CatalystCenter("catc.example.com", "svc-api", "***")
ids = [d["id"] for d in cc.pages("/dna/intent/api/v1/network-device",
                                 {"platformId": "C9300-48P"})]
job = cc.call("POST", "/dna/intent/api/v1/network-device-poller/cli/read-request",
              json={"commands": ["show version", "show ip int brief"],
                    "deviceUuids": ids[:10], "timeout": 0})
task = cc.wait_task(job["response"]["taskId"])
file_id = json.loads(task["progress"])["fileId"]
output = cc.call("GET", f"/dna/intent/api/v1/file/{file_id}")

Use when

  • An engineer is investigating one device or a handful
  • Cached inventory or Assurance data cannot answer the question

Do not use

  • On a timer, in a loop, or across the whole fleet
  • For configuration changes (Command Runner is read-only)

Integrate

AI agents and MCP

Cisco's open-source Catalyst Center MCP server, in beta since August 2026, lets any MCP-capable AI client call generated Catalyst Center API tools. It runs inside your network, so data and the model can stay within an air-gapped boundary.

When to use MCP vs the AI Assistant

Cisco's rule: use the in-product AI Assistant when the work starts in the Cisco product; use MCP when the work starts in a workflow you are building around it, such as a helpdesk tool, self-service portal, cross-vendor copilot, automated report or custom agent.

Use caseWho benefitsExample request
Ticket triage with network evidenceL1 (first-line) helpdeskIs this one user, access point or location? Is the AP healthy? What belongs in the ticket?
End-user self-serviceEmployeesCheck my Wi-Fi connection before I open a case
Inventory and health reviewNOCSummarize health for Global/San Jose; group POOR devices by role
Wireless experience investigationWireless teamWorst APs, SSIDs and clients at HQ over 24 hours, and next checks
Software and compliance risk reviewSecurity and operationsCompliance issues, advisories, field notices, prioritized. Do not make any changes.
Cross-domain copilotPlatform teamsCombine Catalyst Center with Meraki, ITSM or other MCP servers in one agent

MCP best practices

  1. It is not read-only by design. The README states the server adds no authorization layer, does not enforce read-only, and the catalog may include configuration-changing operations. Enforce read-only with an Observer-role account.
  2. One dedicated, least-privilege account per deployment. Treat every connected client as able to call anything that account can.
  3. Keep the endpoint private. Bind to 127.0.0.1; if shared, put it behind your gateway with authentication and TLS.
  4. Keep certificate verification on (CATALYST_CENTER_VERIFY_SSL=true) except in labs.
  5. Match the release branch to the controller and rebuild after each controller upgrade.
  6. State the safety boundary in prompts ("read-only, do not change anything"). It is a backstop, not a control.
  7. Mind rate limits. Agents chain many calls; the same per-operation limits and 500-row pages apply.
  8. Choose the model deliberately. For regulated or air-gapped sites, pair the local server with an approved private model.
  9. Log tool calls on your side. The controller sees only one service account.
  10. Beta can change. Pin a commit and retest on updates.

Guidance checklist

  1. Pin to your release. API version equals controller version; pin SDK, Ansible and Terraform to it.
  2. Read Deprecated and Breaking sections before every upgrade, then test integrations against the target release in a lab.
  3. One service account per integration, least privilege, RBAC v2 roles and access groups.
  4. Cache the token and re-authenticate once on 401; documented lifetimes differ (1 hour vs 60 seconds).
  5. Keep TLS verification on in production.
  6. Treat 202 as accepted, not done. Poll the task with a timeout and surface failureReason.
  7. Page at 500 with a 1-based offset; size with /count, filter with /query, de-duplicate by ID.
  8. Design for 429. Per-operation limits of 50 to 100 per minute; back off and serialize writes.
  9. Push, don't poll. Webhooks for events and issues; reconcile hourly.
  10. Never schedule device-touching calls. Command Runner and Path Trace are on demand, one device at a time.
  11. Prefer the new resource model: /sites, /ipam, /sda, /networkDevices, /networkDeviceImages.
  12. Gate every change on prerequisites: backup, archive, Managed and Reachable, no critical issues, compatibility.
  13. Use bulk operations in waves by site.
  14. Validate before and after: readiness checks, validation workflows, compliance, health.
  15. Put MCP behind an Observer account on loopback. The server does not enforce read-only.
