Foundations

Overview and the four interfaces

Catalyst Center exposes a northbound REST (Representational State Transfer) API (application programming interface) over HTTPS (HTTP Secure) with JSON (JavaScript Object Notation) bodies, called the Intent API. Around it sit an eastbound event channel, a westbound ITSM (IT Service Management) integration, and a southbound multivendor SDK (Software Development Kit) that Cisco has deprecated. Every call goes to https://<cluster> plus a path prefix.

PrefixServesExample
/dna/intent/api/v1/ (v2)Automation and inventory: sites, devices, provisioning, SD-Access, wireless, templates, eventsGET /dna/intent/api/v1/network-device
/dna/data/api/v1/Assurance analytics: query, count, trend, top-N, energyPOST /dna/data/api/v1/assuranceEvents/query
/dna/system/api/v1/ (v2)Platform: authentication, users and roles, backup and restore, system upgradePOST /dna/system/api/v1/auth/token
/dna/campus/api/v1/Campus wireless controller intent (3.2.2, Beta), switch configuration and provisioning (3.2.3, Beta), campus networks (3.3.1, controlled availability)POST /dna/campus/api/v1/switches/configs/status, GET /dna/campus/api/v1/networks

Naming shifted in 2.3.7: older operations use hyphenated singular paths (/network-device); newer ones use camelCase collections with /count and /query siblings (/networkDevices, /networkDevices/query). Prefer the newer form; the older ones are the usual deprecation candidates.

Foundations

Where a call stops

Most reads are answered from the controller's own stores and never touch a device. Writes and live CLI (command-line interface) queries become tasks, and only tasks reach devices. Cost, freshness and safety all follow from which path you hit.

Inventory and design database

Sites, settings, devices, configuration archive. Paged with offset/limit (max 500).

Freshness: last device sync. Periodic resync minimum is 6 hours from 3.1.5, plus event-driven updates.

Assurance data

Health scores, issues, events, analytics. Intent health endpoints plus /dna/data query and trend operations.

Freshness: telemetry ingest from devices (SNMP, syslog, NetFlow, streaming telemetry).

Task engine

Provisioning, SWIM (Software Image Management), discovery, Command Runner. Returns 202 with a taskId.

Freshness: the result exists only once endTime is set.

Live simulation: a day of API traffic

The same three stores, running. Devices stream telemetry into Assurance without any API call. Your dashboard polls site health every five minutes, a CMDB (configuration management database) sync pages through inventory nightly, and webhooks leave the event engine without touching the API gateway. Rate limits are set per operation and counted per client IP address, so each operation has its own meter. Fire a 120-call bulk script at one operation to see that operation reject the overflow with HTTP 429 while the others keep working.

Authentication and RBAC

Authenticate once with HTTP Basic (RFC, Request for Comments, 7617), then send the returned JWT (JSON Web Token) in X-Auth-Token on every call for up to one hour. Every call is then checked against the caller's RBAC (Role-Based Access Control) role.

ItemDetail
Token endpointPOST /dna/system/api/v1/auth/token with Basic credentials; response {"Token": "..."}
HeaderX-Auth-Token: <token> plus Content-Type: application/json
Lifetime1 hour per the Authentication API specification. The Platform User Guides 3.1.x to 3.3.x (API prerequisites) state 60 seconds. Treat the lifetime as unreliable: cache the token, and re-authenticate on any 401.
Code previewsDeveloper Toolkit generates code in Shell, Node, Python, Ruby, JavaScript, jQuery, PHP, Go and Ansible. Generated Python needs the requests library.
Optional AES modeIf enabled in system configuration, the Authorization header carries CSCO-AES-256 credentials= followed by the Base64 encoding of username:password encrypted with the 256-bit AES (Advanced Encryption Standard) key, instead of Basic credentials.
RBACUse RBAC v2 roles (/dna/system/api/v2/roles) and access groups (/dna/system/api/v1/accessGroups) from 3.1.5; v1 role operations are Sunset.
Getting a token for testingPlatform > Developer Toolkit > Authentication > Authentication API > Try, or Postman / Bruno with Basic auth. Cisco's tech note sets the token once as a collection-level header.
Service accountsCisco's lab examples use a SUPER-ADMIN-ROLE login; in production use one account per integration. OBSERVER-ROLE for read-only collectors and MCP (Model Context Protocol) servers; a narrow custom role for writers.
TLS (Transport Layer Security)Labs disable verification for self-signed certificates; in production import the cluster CA (Certificate Authority) and keep verification on.
Python · minimal client used by every example in this guide
# catalyst_client.py: token cache, 401 re-auth, 429 backoff, task poller, pager
import json, time, requests
from requests.auth import HTTPBasicAuth

class CatalystCenter:
    def __init__(self, host, user, password, verify=True):
        self.base = f"https://{host}"
        self.s = requests.Session(); self.s.verify = verify
        self.auth = HTTPBasicAuth(user, password); self.exp = 0

    def _login(self):
        r = self.s.post(f"{self.base}/dna/system/api/v1/auth/token", auth=self.auth)
        r.raise_for_status()
        self.s.headers.update({"X-Auth-Token": r.json()["Token"],
                               "Content-Type": "application/json"})
        self.exp = time.time() + 55 * 60          # API reference: 60 min

    def call(self, method, path, **kw):
        if time.time() > self.exp:
            self._login()
        delay, relogged = 2, False
        for _ in range(6):
            r = self.s.request(method, self.base + path, **kw)
            if r.status_code == 401 and not relogged:
                self._login(); relogged = True; continue
            # 429 any method; 500/503 only for reads (a write may already have run)
            if r.status_code == 429 or (r.status_code in (500, 503) and method == "GET"):
                ra = r.headers.get("Retry-After", "")   # not documented; honour if sent
                time.sleep(int(ra) if ra.isdigit() else delay)
                delay = min(delay * 2, 60); continue
            r.raise_for_status()
            return r.json() if r.content else {}
        raise RuntimeError(f"gave up: {method} {path}")

    def wait_task(self, task_id, timeout=900, every=5):
        # GET /tasks/{id} (2.3.7.6+); the older /task/{taskId} is Sunset
        t0 = time.time()
        while time.time() - t0 < timeout:
            t = self.call("GET", f"/dna/intent/api/v1/tasks/{task_id}")["response"]
            if t.get("status") == "FAILURE":
                d = self.task_detail(task_id)
                raise RuntimeError(d.get("failureReason") or d.get("errorCode"))
            if t.get("status") == "SUCCESS":
                return t                           # endTime, resultLocation set
            time.sleep(every)                      # PENDING
        raise TimeoutError(task_id)

    def task_detail(self, task_id):              # progress, data, failureReason
        return self.call("GET", f"/dna/intent/api/v1/tasks/{task_id}/detail")["response"]

    def task_file_id(self, task_id):
        # Cisco documents the fileId in the legacy task's progress; try the new
        # detail first, then fall back to /task/{taskId} (Sunset, still answering)
        for path in (f"/tasks/{task_id}/detail", f"/task/{task_id}"):
            try:
                return json.loads(self.call("GET", "/dna/intent/api/v1" + path)["response"]["progress"])["fileId"]
            except (KeyError, TypeError, ValueError, RuntimeError, requests.RequestException):
                continue
        raise RuntimeError(f"no fileId for task {task_id}")

    def pages(self, path, params=None, limit=500, start=1):
        # Most list operations: 1-based offset, limit up to 500. Check each one:
        # site-health allows 50, some event operations start at 0.
        offset = start
        while True:
            rows = self.call("GET", path, params={**(params or {}),
                             "offset": offset, "limit": limit})["response"]
            yield from rows
            if len(rows) < limit:
                return
            offset += limit

Foundations

Async tasks, pagination, rate limits

Most writes are tasks

A 202 Accepted means the request was queued, not that it worked. Poll GET /dna/intent/api/v1/tasks/{id} until status is SUCCESS or FAILURE; on failure read failureReason from /tasks/{id}/detail. The older GET /task/{taskId} (with endTime and isError) has been Sunset since 2.3.7.6; it still answers, and the 202 body's url still points at it. The legacy /business/sda/... APIs return executionId instead; poll /dna/intent/api/v1/dnacaap/management/execution-status/{executionId}. A few writes return a status URL or answer synchronously; read each operation's response.

Pagination and filtering

RuleDetail
Page sizelimit 1 to 500 on most list operations (devices, sites, SD-Access objects). Not a global rule: site-health allows 50, audit logs 25, the interfaces query 1,000. Read each operation's limit.
Offsetoffset is 1-based on most list operations; some event-management operations start at 0. Loop until a page returns fewer than limit rows.
Size firstCall the matching /count operation to size a job.
Complex filtersPrefer POST …/query operations for filters, sorting and aggregation.
Unstable site pagingBefore the 3.2.3 software maintenance update (SMU) 75346.100, repeated calls with the same limit and offset could return different site IDs (CSCwu68404, listed as resolved in the 3.2.3 release notes). On older builds, sort client-side and de-duplicate by ID; 3.3.1 adds sortBy and order to Get Sites.

Rate limits

SourceWhat it says
OpenAPI specs on DevNetPer operation, and they vary widely: 10 per minute (roles), 50 (add fabric site), 100 (get sites), 1,000 (get tasks)

Rate-limit budget calculator

Default 50 per the Platform User Guide; read the real limit on each operation's Features tab. Per-record detail calls are what usually blow the budget.

Automate

Templates and provisioning Writes config (async) Reaches the device

Configuration templates (CLI or Velocity/Jinja) are the main way to push custom configuration in both fabric and non-fabric networks. The safe sequence is author, version, preview, then deploy.

  1. Create a project and template in Template Programmer
  2. Commit a version (deployments use committed versions)
  3. Preview the rendered config for one device
  4. Deploy with the v2 operation and get a taskId (v1 returns a deploymentId)
  5. Poll the task (or the v1 deployment status), then run compliance
Endpoint familyFunction
GET /dna/intent/api/v2/template-programmer/projectFind projects and template IDs
POST /dna/intent/api/v2/template-programmer/template/deployDeploy a committed template; returns a taskId to poll with /tasks/{id} (the Python SDK uses v2 by default from 3.2.3)
POST /dna/intent/api/v1/template-programmer/template/deployOlder deploy operation, still supported; returns a deploymentId
GET /dna/intent/api/v1/template-programmer/template/deploy/status/{deploymentId}Poll a v1 deployment until it reports success or failure
Network profiles and site assignmentBind templates to sites through profiles so new devices inherit them
Wired and wireless provisioning operationsAssign a device to a site and push the site's intent

Track a v2 deployment with the task API and a v1 deployment with its own status endpoint; do not mix them. Template variables are usually filled from a CMDB or IPAM record. Keep templates idempotent and avoid lines that the controller's own intent also writes, or compliance will flag drift.

Python · upgrade wave skeleton (dist_body and act_body follow your release's schema)
# 1. Devices behind the golden image for one site (2.3.7.9+)
outdated = list(cc.pages("/dna/intent/api/v1/networkDeviceImages",
                         {"networkDeviceImageStatus": "OUTDATED",
                          "siteId": SITE_ID, "sortBy": "id", "order": "asc"}))
# 2. Readiness: start each check, wait for it, keep only devices that pass
ready = []
for dev in outdated:
    t = cc.call("POST", f"/dna/intent/api/v1/networkDeviceImages/{dev['id']}/readinessChecks")
    try:
        done = cc.wait_task(t["response"]["taskId"])
    except (RuntimeError, TimeoutError):
        continue                                   # check failed or timed out: leave it out
    # resultLocation points to this run's validation results
    results = cc.call("GET", done["resultLocation"]).get("response", [])
    if not any(v.get("status") == "FAILED" for v in results):
        ready.append(dev["id"])
# 3. Distribute ahead of the window (build the body from your release's schema)
t = cc.call("POST", "/dna/intent/api/v1/networkDeviceImages/distribute/bulk", json=dist_body(ready))
cc.wait_task(t["response"]["taskId"], timeout=3600)
# 4. Maintenance window for the approved change (suppresses Assurance alerts)
m = cc.call("POST", "/dna/intent/api/v1/networkDeviceMaintenanceSchedules", json={
    "description": "CHG0012345 image upgrade", "networkDeviceIds": ready,
    "maintenanceSchedule": {"startTime": WINDOW_START_MS, "endTime": WINDOW_END_MS}})
cc.wait_task(m["response"]["taskId"])
# 5. Activate inside the window, then read post-check results
t = cc.call("POST", "/dna/intent/api/v1/networkDeviceImages/activate/bulk", json=act_body(ready))
cc.wait_task(t["response"]["taskId"], timeout=5400)
for dev_id in ready:
    post = cc.call("GET", "/dna/intent/api/v1/networkDeviceImages/validationResults",
                   params={"networkDeviceId": dev_id, "type": "POST_VALIDATION"})

Fabric vs non-fabric: same API?

Yes for the platform, no for the overlay. Authentication, sites and settings, inventory, discovery, PnP, templates, SWIM, compliance, Assurance and events are the same operations in both. SD-Access adds its own domains for the fabric overlay, and wireless splits into a non-fabric and a fabric family.

Use the /dna/intent/api/v1/sda/... family. The older /business/sda/... operations (about 45: fabric, fabric site and zone, edge, border and control-plane devices, authentication profile, host onboarding, provisioning, transits, virtual networks, multicast) were deprecated in 2.3.7.9; they still answer with a Sunset banner. Events and webhooks Stops at the controller

When a subscribed event fires, Catalyst Center makes an HTTP POST or PUT to your listener with a JSON payload. Destinations can be REST webhook, email, syslog or SNMP trap, each with its own API; ITSM instances also have one (/dna/intent/api/v1/integration-settings/instances/itsm), and Webex is set up in the UI (user interface). Event definitions are fixed and cannot be edited.

Python · register a webhook, subscribe, reconcile
# 1. Webhook destination. trustCert True skips certificate checks: lab only.
cc.call("POST", "/dna/intent/api/v1/event/webhook", json={
    "name": "noc-listener", "description": "NOC event intake",
    "url": "https://hooks.example.com/catc", "method": "POST",
    "trustCert": False})
# 2. The create call returns no ID: look the destination up by name
dest = cc.call("GET", "/dna/intent/api/v1/event/subscription-details/rest",
               params={"name": "noc-listener"})
instance_id = dest[0]["instanceId"]
# 3. Subscribe unreachable events (switch, router, WLC) to it
UNREACHABLE = ["NETWORK-NON-FABRIC_WIRED-1-200",      # switch unreachable
               "NETWORK-NON-FABRIC_WIRED-1-250",      # router unreachable
               "NETWORK-NON-FABRIC_WIRELESS-1-150"]   # WLC unreachable
cc.call("POST", "/dna/intent/api/v1/event/subscription/rest", json=[{
    "name": "network-device-unreachable",
    "subscriptionEndpoints": [{"instanceId": instance_id,
        "subscriptionDetails": {"connectorType": "REST"}}],
    "filter": {"eventIds": UNREACHABLE}}])

# Hourly reconcile: published notifications the listener may have missed
now_ms = int(time.time() * 1000)
missed = [n for eid in UNREACHABLE
          for n in cc.call("GET", "/dna/intent/api/v1/event/event-series",
                           params={"eventIds": eid, "startTime": now_ms - 3600000,
                                   "endTime": now_ms})]

Cisco's stated practice: confirm HTTP/HTTPS reachability from the cluster to your listener before subscribing. An HTTP/S proxy can be set for outbound notifications. Keep trustCert false so the controller verifies your listener's certificate; true is for lab listeners with self-signed certificates. The unreachable event IDs above come from Cisco's Event Catalog (Platform > Developer Toolkit > Event Notifications); third-party devices use NETWORK-NON-FABRIC_WIRED-1-273.

Command Runner runs read-only CLI commands on a list of devices; the allowed command keywords are listed by GET /network-device-poller/cli/legit-reads. AI agents and MCP

Cisco's open-source Catalyst Center MCP (Model Context Protocol) server, in beta since August 2026, lets any MCP-capable AI client call generated Catalyst Center API tools. The server runs inside your network; the data stays inside only if the AI client and its model do too, so pair it with a private model where that matters.

When to use MCP vs the AI Assistant

Cisco's rule: use the in-product AI Assistant when the work starts in the Cisco product; use MCP when the work starts in a workflow you are building around it, such as a helpdesk tool, self-service portal, cross-vendor copilot, automated report or custom agent.

MCP best practices

  1. It is not read-only by design. The README states the server adds no authorization layer and does not enforce read-only. The tool catalogs are mostly reads, but some include POST operations (the 2.3.7.11 bundle includes compliance remediation, which changes device configuration). Enforce read-only with an Observer-role account.
  2. One dedicated, least-privilege account per deployment. Treat every connected client as able to call anything that account can.
  3. Keep the endpoint private. Bind to 127.0.0.1; if shared, put it behind your gateway with authentication and TLS.
  4. Turn certificate verification on (CATALYST_CENTER_VERIFY_SSL=true): the server's default is off, and the repository's compose file binds port 7001 on all interfaces, so do not use it as-is.
  5. Match the release branch to the controller: release/2.3.7.11, release/3.1.6 and release/3.2.3 exist today. Rebuild after each controller upgrade; /v1/readiness checks the configuration.
  6. State the safety boundary in prompts ("read-only, do not change anything"). It is a backstop, not a control.
  7. Mind rate limits. Agents chain many calls; the same per-operation limits and 500-row pages apply.
  8. Choose the model deliberately. For regulated or air-gapped sites, pair the local server with an approved private model.
  9. Log tool calls on your side. The controller sees only one service account.
  10. Beta can change. Pin a commit and retest on updates.

Guidance checklist

  1. Pin to your release. Set the SDK's API version to the supported value nearest your controller and pin Ansible and Terraform to versions that support it.
  2. Read Deprecated and Breaking sections before every upgrade, then test integrations against the target release in a lab.
  3. One service account per integration, least privilege, RBAC v2 roles and access groups.
  4. Cache the token and re-authenticate once on 401; documented lifetimes differ (1 hour vs 60 seconds).
  5. Keep TLS verification on in production.
  6. Treat 202 as accepted, not done. Poll /tasks/{id} with a timeout and surface failureReason from /tasks/{id}/detail.
  7. Page with each operation's limit and offset base; usually 500 and 1-based. Size with /count, filter with /query, de-duplicate by ID.
  8. Design for 429. Limits are per operation (from 10 to 1,000 per minute) and counted per client IP address; back off and serialize writes.
  9. Retry writes carefully. Retry 500 and 503 only for reads; for a write, check the task or object first.
  10. Push, don't poll. Webhooks for events and issues; reconcile hourly from the published notifications.
  11. Never schedule device-touching calls. Command Runner and Path Trace are on demand, for a handful of devices or one flow.
  12. Prefer the new resource model: /sites, /ipam, /sda, /networkDevices, /networkDeviceImages, /tasks, assuranceIssues.
  13. Gate every change on prerequisites: backup, archive, managed and reachable, no critical issues, SD-Access compliance.
  14. Use bulk operations in waves by site.
  15. Validate before and after: readiness checks, validation workflows, compliance, health.
  16. Put MCP behind an Observer account on loopback. The server does not enforce read-only, and certificate checks are off unless you turn them on.
